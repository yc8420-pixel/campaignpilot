## 十分钟讲解提纲

1. **1 分钟：问题和范围。** 零散生成文案难以追溯依据、审核版本与效果数据；先解决一条小而完整的链路。
2. **3 分钟：走产品。** 按上面的三分钟流程，重点停留来源、审核与复盘。
3. **2 分钟：关键实现。** 同一领域规则用于两模式；CAS 保护输入版本；Postgres 原子 RPC 绑定 run 与输出；指标用确定性计算。
4. **2 分钟：可靠性。** unknown 处理、防重复导入、批次整体验证、server key 的归属校验、固定样例与真实生成分开。
5. **1 分钟：验证证据。** 打开验收报告和一个失败场景测试，说明测了什么、没有测什么。
6. **1 分钟：取舍。** 聚合存储适合个人作品，扩展时拆表；没有跨渠道归因引擎和真实投放成效结论。

## 常见追问

**为什么不只做聊天窗口？** 因为工作结果需要保存输入版本、人工审核、导出及指标关联；聊天回答本身不足以支撑交付。

**如何防幻觉？** 限定已确认事实、结构化响应、引用与部分事实规则、人工复核；这些是多道约束，不是“幻觉已被彻底解决”的证明。

**为什么不用 AI 算 CTR？** 同一数据必须给出可复算结果，AI 负责解释与建议；金额用整数分，汇总按分子分母加总后计算。

**修改内容后旧数据算谁的？** 交付版本固定，实质改稿新建 variant，已有指标继续引用原变体与版本。

**超时会不会扣费？** 可能。结果不明记 unknown，保留费用预留；重试由人显式选择，不承诺退款或零费用。

**数据库用了 RLS，为什么还查 owner？** 服务端 secret key 会绕过 RLS，必须在 API 和 RPC 入口检查资源归属，不能只靠前端。

**有什么效果数据？** 只有模拟黄金数据和本机性能样本。没有真实投放或效率对照实验，不能报转化/效率提升百分比。

**哪些是本人做的？** 本项目使用 AI 辅助完成实现与验证。个人在需求判断、取舍、检查与讲解上的贡献应按真实参与说明，不能把工具代写夸大成完全独立手写。
