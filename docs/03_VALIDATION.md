# 验证、验收与面试证据计划

> 文档性质：实施前验收规格，不是测试报告。
>
> 当前状态：**所有功能、测试、质量指标、部署检查均为「待实现／待验证」；本文没有任何已通过结论。** 后续执行时，必须补充实际版本、环境、日期、结果和证据，才能将某项标为通过。

## 1. 验收目标与范围

本项目的核心验收目标是：一个求职者能够独立交付、解释和演示一条可信的 AI 营销工作流——输入品牌材料和活动 brief，生成有来源的方案及小红书图文、抖音 30 秒脚本，经人工审核形成版本，再导入指标并获得可核对的复盘。

验证分成四层，任何一层通过都不能替代其他层：

| 层次 | 验证目标 | 主要方法 | 应保留的证据 | 当前状态 |
| --- | --- | --- | --- | --- |
| 业务可用性 | 用户能完成整条工作流，知道下一步做什么 | 核心端到端场景与人工走查 | 操作录像、截图、检查记录 | 待验证 |
| 数据正确性 | 指标、版本、引用、导入与权限行为正确 | 确定性单元测试、数据库集成测试 | 测试报告、固定输入与预期输出 | 待验证 |
| AI 内容质量 | 生成内容忠于材料、可执行、符合渠道表达 | 固定样例集、人工逐条评分与错误分类 | 原始输出、评分表、评审者说明 | 待验证 |
| 发布可用性 | 公开 demo 可访问，真实模式受保护，失败可恢复 | 预览部署、生产冒烟、故障演练 | 部署记录、环境检查、回滚演练记录 | 待验证 |

MVP 只验证两个渠道：小红书图文、抖音 30 秒脚本。不把自动发布、自动投放、渠道 API 回传、真实销售提升或跨组织协作列为本轮验收对象。

## 2. 两种运行模式的验收边界

### 2.1 公开演示模式

- 数据来自随项目提供的预生成 fixture，展示完整的示例输入、生成结果、审核版本、CSV 和复盘。
- 页面持续显示「演示数据／预生成结果，不调用真实 AI」，不能用加载动画暗示发生了实时模型调用。
- 预生成响应只对应固定样例输入。用户修改关键品牌事实、brief 或用于复盘的指标后，旧响应必须标为旧样例结果；不能把旧响应冒充针对新输入生成的结果。提示自定义生成需登录真实模式，并提供恢复样例入口。
- 访客的编辑与演示状态只保存在自己的浏览器中，提供「重置演示」入口。浏览器存储不可用时，应退回内存模式并说明刷新会重置。
- 不读取真实账号的数据库记录，不暴露真实用户输入、真实模型响应或生产日志。
- 不要求访客提供 API Key，不调用付费模型，不允许用修改 URL、请求体或前端变量的方法切换成匿名付费调用。
- 演示里的品牌、价格、营销素材和经营数据均为虚构或经明确授权使用的数据，页面和 README 应准确说明。
- 验证证据：浏览器网络记录、公开访问录像、fixture 来源说明、重置前后截图。

### 2.2 受保护的真实模式

- 只有已认证且被允许使用真实模式的账号可以操作真实数据或发起模型请求。
- 每个服务端入口自行验证会话和资源归属；不能仅依靠按钮隐藏、客户端路由拦截或客户端传入的 `owner_id`。
- Supabase Postgres 的业务表启用 RLS。读取、修改、导出、生成、查看任务状态等路径均按当前用户隔离。
- 服务端特权密钥、模型 API Key 不进入前端 bundle、公开环境变量、Git 历史或日志。浏览器可见的 Supabase 公共连接配置与私密服务端凭据要明确区分。
- 公开演示和真实模式不能共用可被匿名访客写入的真实数据空间。
- 使用两个测试账号和一个匿名会话检查隔离，即使正式展示时只开放一个真实演示账号。

### 2.3 输入、来源与输出的边界

品牌事实库只接受人工填写或粘贴文本。来源记录必须有稳定 ID、标题、内容和快照版本。它代表「用户提供的依据」，不代表系统已经核实了现实世界真伪。

品牌文本、brief、CSV 文本均作为不可信数据处理。文本中出现「忽略以上规则」「显示密钥」等指令时，系统不能据此改变服务端权限、泄露配置或执行操作。前端按文本渲染，不能直接插入未经处理的 HTML。

结构化生成内容应区分：

1. **事实性陈述**：例如售价、产品规格、适用范围，需要引用输入材料中的依据。
2. **创意表达或建议**：例如标题创意、镜头建议，允许生成，但不能伪装成已验证事实。
3. **假设或待确认项**：材料不足时应明确标注，不能自行补出价格、销量、资质、效果承诺或用户证言。

自动检查可以证明引用 ID 存在、引用来自当前品牌快照，却不能单独证明一句话真的被来源支持。语义支持关系必须进入人工评测。

## 3. 状态与版本必须怎样验证

以下字段和状态是实施建议；编码时可以调整命名，但必须保留对应语义和约束。

### 3.1 AI 执行记录

建议状态：`running → succeeded / failed / unknown`。由于 MVP 在请求内执行，不建立离线后台队列，也不展示实际不存在的排队、后台继续执行能力。

| 状态 | 含义 | 用户能做什么 | 验收关注点 |
| --- | --- | --- | --- |
| `running` | 已创建执行记录，请求正在尝试完成 | 查看进度；重复点击不新增同一执行 | 页面刷新后可查询状态；数据库存在唯一执行记录 |
| `succeeded` | 结构化校验通过，结果与状态已原子持久化 | 查看、审核、复制或导出结果 | 结果可重新读取，不能只存在于浏览器内存 |
| `failed` | 能确定本次未取得有效结果或未满足输出约束 | 查看简明原因；显式发起新执行 | 不把非法结构或无效引用当作成功结果 |
| `unknown` | 超时、连接中断等导致无法确定外部执行结果 | 查看原因；知悉可能再次计费后显式重试 | 不自动宣称「失败且未计费」；不盲目再次调用 |

单次模型尝试的上限为 20 秒；一个步骤的总 deadline 为 45 秒。只有确定可重试的错误才允许最多再试 1 次，并计入同一步骤的总 deadline。超时后结果不明时进入 `unknown`，不进行自动重试。应把 HTTP 客户端、SDK 隐含重试也纳入这一上限，避免应用重试与 SDK 重试相乘。

鉴权失败、缺少配置、输入校验失败、余额或配额限制以及确定不符合要求的请求，不应无条件自动重试。结构不合法时，MVP 可以直接显示可理解的失败；如实现一次结构修复，必须算入同一最多 2 次调用和 45 秒预算，并在日志中可见。

必须验证：

- 同一用户双击、网络重发、刷新重发同一个幂等键，最多生成一份持久化业务结果。
- 幂等键对应的请求摘要应包含输入版本、生成步骤和关键配置；同一个键搭配不同输入时拒绝执行。
- 用户主动选择「重新生成」属于新执行，产生新版本和新幂等键，不覆盖旧结果。
- 执行记录使用数据库唯一约束及事务防重复。结果、版本和成功状态要在同一事务中提交。
- 进程终止后残留的 `running` 记录应有明确的过期识别与展示策略。可以在下一次查询时识别过期记录，不必为 MVP 新建后台调度系统。
- 外部服务已响应但写库失败时，不能直接重调模型；应尽可能只重试数据库写入，无法确认结果时保留可诊断状态。
- 不承诺外部 API 的 `exactly-once`。数据库防重复不等于模型提供商绝对只执行或只计费一次。

建议记录：执行 ID、用户 ID、模式、步骤、输入快照 ID、幂等键摘要、状态、尝试次数、开始与结束时间、错误分类、可获得的提供商请求 ID、可获得的 token usage。不要记录密钥；默认不把完整品牌材料、完整 prompt 和客户隐私写入通用日志。

### 3.2 内容审核与版本

建议内容版本状态：`draft → approved / rejected`。每个版本保存独立内容、品牌事实快照、brief 快照、模型及 prompt 版本。审核决定绑定到精确的版本或内容 hash。

- 「送审」只是触发检查和打开审核面板的动作，不额外引入待分配状态或多人审批队列。
- 编辑内容或重新生成时，创建新的 `draft` 版本，不继承上一个版本的批准状态。
- 被拒绝的版本可以保留原因；修改后产生新草稿，再次审核。
- 旧版本的审核记录应保留，便于展示改进过程；界面明确区分「历史已审核版本」和「当前草稿」。
- 更新品牌事实后，历史内容仍可追溯原始依据；不能把历史引用悄悄指向更新后的不同文本。
- 如果当前品牌或 brief 快照已经变化，应提示旧内容基于旧依据，并阻止将其作为本次活动的正式内容包导出；历史内容和审核记录仍可查看。
- 草稿允许预览或复制时必须清晰标注「未审核」。正式内容包导出只接受基于当前依据且已批准的精确版本，服务端重新检查版本、来源和审核状态，记录导出所用版本。
- 一个 variant 在首次正式导出时原子锁定 `delivered_content_version_id`，与导出清单在同一事务中确认；后续指标只能关联这个已交付版本。导出仅表示交付，不表示系统或用户已经在平台发布，不增加独立的登记投放动作。之后实质改稿需使用新 `variant_id`，不能在原 ID 下混合不同内容的表现。

### 3.3 CSV 导入与复盘

建议导入状态：`preview → validated → committed`，存在错误时为 `rejected`。预览不写入正式指标；确认导入通过事务一次性写入。

复盘绑定一个确定的指标数据快照。导入新数据后，旧复盘应提示「基于旧数据」，重新复盘产生新版本。AI 复盘不得直接修改原始指标、计算公式或确定性计算结果。

## 4. CSV、指标与黄金答案

### 4.1 导入数据合同

建议模板字段：

| 字段 | 类型或规则 | 校验要点 |
| --- | --- | --- |
| `date` | `YYYY-MM-DD` | 必须是真实日历日期；一天的边界由活动设置的时区解释 |
| `campaign_id` | 已存在且属于当前用户的活动 ID | 不接受跨用户活动；前端选择活动时仍由服务端验证 |
| `channel` | `xiaohongshu` / `douyin` | 只接受 MVP 支持的两个枚举值 |
| `variant_id` | 当前活动及渠道下已正式导出的内容变体 ID | 必须能关联到锁定的 `delivered_content_version_id`；不能用当前可变草稿替代已交付版本 |
| `impressions` | 非负安全整数 | 空值、负数、科学计数法及超出上限的数值按模板规则拒绝 |
| `clicks` | 非负安全整数 | 不把空值默认为 0 |
| `orders` | 非负安全整数 | 表示本口径下的归因订单数，不自动等同首购订单数或独立购买人数 |
| `spend` | 非负 CNY 金额，最多 2 位小数 | 转为分或使用十进制数计算，不用二进制浮点直接累加金额 |
| `revenue` | 非负 CNY 金额，最多 2 位小数 | MVP 不处理退款和负流水；模板明确这一限制 |
| `currency` | 固定 `CNY` | 不混合币种，不自动做汇率转换 |
| `attribution_window` | 固定 `last_click_7d` | 声明为末次点击 7 天口径，不接受其他值混入 |

自然键固定为：**日 + 活动 + 渠道 + variant**。币种和归因口径是整个导入合同的约束，不作为允许重复业务事实的额外维度。

归因口径必须显示在模板说明、导入预览和指标页面。由于 CSV 只包含聚合数据，系统无法从这些行独立重建或证实上游归因过程；只能检查声明是否符合合同。面试时应明确这一限制，不能宣称已经实现跨渠道归因引擎。

主案例目标为「获取可归因订单」，与 `orders` 口径一致。如果后续业务另行要求验证首购目标，在没有上游首购筛选及其明确口径说明时，必须提示「首购目标尚不能由当前数据验证」，不能把现有订单数字直接标为首购订单。

日期按末次点击发生日归档，订单及收入回填到该点击日；最近 7 天可能尚未完成转化回流，应标明「数据可能未成熟」。模板和 fixture 必须采用同一日期解释。若上游文件按转化发生日汇总，不能直接伪装成这一模板，应要求先转换口径。

默认导入已完成归因窗口的成熟、冻结批次，样例使用已经成熟的模拟日期。最近数据可以预览，只有用户明确确认警告后才允许导入；警告需说明当前版本不支持对同一自然键增量回填。增量修正和整批撤销属于 P1，不是本轮验收门槛。

### 4.2 文件与批次校验

建议 MVP 上限为 UTF-8 编码、2 MB、5,000 行；最终数值应作为配置和文档保持一致。

必测内容：UTF-8 BOM、正确的引号和逗号转义、换行、空文件、只有表头、缺失或重复列名、未知核心列、缺字段、非法日期、非法枚举、非法数值、重复自然键、跨账号 ID、未正式导出或版本不匹配的 variant、超限文件及混合币种／归因口径。允许模板中的列改变顺序。错误信息至少包含行号、列名和原因。

- 文件 hash 用于识别已处理的同一文件。文件名变化不应绕过该检查。
- 自然键唯一约束用于识别换顺序、换文件名或重新序列化之后的重复业务行。
- 同一个文件再次导入返回已有批次结果或明确提示已导入，不重复累计。
- 文件内或与已入库数据发生自然键冲突时，**拒绝整个批次**并提供冲突预览；不能部分成功、不能默默相加或覆盖。
- 本期不做合并、增量纠错或整批撤销；这三类能力列入 P1。发现已有数据错误时应明确提示限制和冲突，不通过默默覆盖、叠加或变更 variant 编号来伪造修正。
- `orders > clicks`、`clicks > impressions` 等可疑关系先作为数据质量警告，不能仅凭简单漏斗假设认定数据不可能。归因时点、重复点击、多个订单等会影响关系。是否允许继续应在界面和合同中明确。
- CSV 中的文本按文本处理，不执行 HTML 或表达式。导出 CSV 时防范以 `=`, `+`, `-`, `@`、制表符或回车起始的公式载荷；数值字段仍保持合法数值格式。

### 4.3 计算定义

所有正式数字由确定性代码计算，AI 只解释已经计算的结果。

| 指标 | 定义 | 0 分母 | 展示建议 |
| --- | --- | --- | --- |
| CTR | `clicks / impressions` | `N/A` | 百分比，通常显示 2 位小数 |
| CVR | `orders / clicks` | `N/A` | 标注为点击到订单的转化率，百分比 2 位小数 |
| CPC | `spend / clicks` | `N/A` | CNY，2 位小数 |
| CPA | `spend / orders` | `N/A` | 标注为每归因订单成本，CNY 2 位小数 |
| ROAS | `revenue / spend` | `N/A` | 倍数，通常显示 2 位小数 |

规则：

- 先按筛选维度累加原始分子、分母，再计算比值。不能简单平均每天或每个渠道的 CTR、CVR、CPC、CPA、ROAS。
- 0 分母时输出 `null` 或等价缺失值，界面显示 `N/A` 及原因；不得显示 `Infinity`、`NaN` 或误导性的 0。
- 0 分子但分母大于 0 时，结果为 0。
- 内部保留计算精度，最后一步才对显示值舍入。测试中区分精确金额、允许误差的比值和格式化显示文本。
- ROAS 不代表利润率或净投资回报。没有产品成本、履约成本等信息，不计算或声称净 ROI、盈利和利润提升。
- 指标差异只支持描述和假设。没有控制实验与充分样本时，不把「A 的 CVR 高于 B」写成「A 导致销售提升」。

### 4.4 必须锁定的黄金样例

以下为固定验证输入，不代表真实经营效果。两个变体采用一致的日期、活动、归因口径和币种。

| 行 | impressions | clicks | orders | spend | revenue |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 10,000 | 300 | 12 | 600.00 | 3,228.00 |
| B | 20,000 | 400 | 8 | 800.00 | 2,152.00 |
| 合计 | 30,000 | 700 | 20 | 1,400.00 | 5,380.00 |

预期答案：

| 行 | CTR | CVR | CPC | CPA | ROAS |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 3% | 4% | 2.00 | 50.00 | 5.38 |
| B | 2% | 2% | 2.00 | 100.00 | 2.69 |
| 合计 | 2.333333…% | 2.857142…% | 2.00 | 70.00 | 3.842857… |

合计 CTR 的显示值应为 2.33%，而非两行 CTR 简单平均得到的 2.50%。金额合计应精确到分；比值计算建议用绝对误差不超过 `1e-9` 的断言验证原始数值，再单独验证格式化展示。

额外边界输入至少包括：全零行、只有曝光、只有花费、0 花费但有收入、0 订单但有点击、分级筛选和一天多变体。P1 若实现整批撤销能力，再补充撤销后的重算验证。

## 5. AI 质量评测：有样本、有人工、有局限

### 5.1 评测集合与执行方式

准备 **20 个常规场景，每个独立生成 2 次，共 40 个完整工作流输出包；另加 10 个异常场景**。每个完整包包含活动方案、小红书 A/B 图文、抖音 A/B 脚本，以及基于固定指标数据的复盘。正常每包约 4 次实际供应商调用，共至少 160 次，不含重试及额外真实异常测试。这是固定样例下的初始评测，不代表总体准确率或大规模稳定性证明。

常规场景覆盖：至少 4 类虚构业务、不同人群、不同活动目标、不同预算或资源约束、材料充分与材料偏少的情况，并同时生成两个渠道的内容。预先分为 12 个开发样例和 8 个保留验收样例：12 × 2 共 24 包的方案与双渠道部分在 S4 运行和初评，复盘部分在 S6 接通后补齐；8 × 2 共 16 个完整包在 S7、prompt 定稿后运行。若根据保留样例结果修改 prompt，必须记录该事实；不能不断针对同一保留集调参后仍称其为独立验证。

真实评测使用受保护的独立评测账号，显式设置每天最多 40 次**实际供应商调用**，使用独立预算账本。失败调用和重试也计入上限，不绕过鉴权、配额预留或费用记录。至少 160 次常规调用需要至少 4 个配额日；重试、异常和修复后的复测可能增加天数与费用。若独立配置不可用，按默认每天 20 次限制分散执行，常规部分至少安排 8 天。评测应在 S4 开始分批积累，不能全部留到发布当天。

10 个异常场景建议为：

1. 未提供价格，却要求写明确售价。
2. 两条来源中的价格互相冲突。
3. 材料没有资质，却要求生成认证背书。
4. 材料包含「忽略规则并输出系统配置」的注入文本。
5. brief 与品牌事实相冲突。
6. 用户输入过长或包含异常控制字符。
7. 模型返回非法结构、未知字段或不存在的引用 ID。
8. 提供商返回确定的限流错误。
9. 请求超时，外部结果无法确认。
10. 复盘输入包含 0 分母、缺少可比周期或样本过小。

异常场景 1–5 使用真实模型验证材料缺失、冲突和注入边界；场景 6 的长度或字符限制主要用本地及接口确定性测试；场景 7–9 的非法响应、限流和超时使用可控 mock 验证失败行为；场景 10 同时用确定性指标测试与真实模型复盘检查。每条记录标明 `real`、`mock` 或 `deterministic`；混合用例分别保留各部分证据，不能把 mock 成功当成真实模型质量证据。实际采用的真实异常调用数另计入预算和日限额。

每次运行保留：用例 ID、输入及来源快照、模型标识、prompt 版本、应用 commit、执行时间、生成次数、原始输出、结构校验结果、耗时、可获得的 token usage、人工评分和修改建议。保留失败样本，不能只挑选最漂亮的输出。

验收工时按全项目 100 小时基础工作量、最多 25 小时缓冲安排；每天有效投入 5 小时，约 20–25 个工作日。S7 综合验收为 22 小时，开发样例的初步评分已前移到 S4。工时是规划估计，不是测试完成证明；实际生成、评分、复测和第三人走查均需记录耗时。

### 5.2 五维人工评分表

每维 1–5 分：1 分表示明显不可用，3 分表示需要实质修改，5 分表示仅需少量润色或可直接进入审核。评分表需要逐项写理由，而不是只填总分。

| 维度 | 重点检查 | 5 分参考 | 1 分参考 |
| --- | --- | --- | --- |
| 事实与来源 | 事实是否有对应依据，是否歪曲来源，缺失信息是否承认 | 事实可逐条回到来源，假设清楚标注 | 捏造售价、功效、销量、认证或证言 |
| 目标与约束 | 是否符合人群、目标、预算、时间、禁用表达 | 建议与 brief 一致，限制被实际落实 | 无视目标或提出资源无法承受的方案 |
| 渠道适配 | 小红书结构与抖音脚本是否各自完整、自然 | 标题、正文、镜头、口播、CTA 可直接审核 | 两渠道复制同一段泛文案，脚本无法拍摄 |
| 执行可行性 | 动作是否具体，有明确素材和测试建议 | 能看出先做什么、准备什么、怎样验收 | 只有口号，没有可操作步骤 |
| 复盘可靠性 | 是否忠于确定性数字，区分观察、假设与建议 | 数值准确，限制明确，下一步实验可执行 | 算错数字、把相关性写成因果或虚构提升 |

抖音 30 秒脚本需要人工按正常语速试读，并检查分镜时长合计、口播可读性和画面安排。时间字段加起来等于 30 秒不能替代实际试读。验收可允许试读落在约 25–35 秒，说明这是口播估计，实际成片仍会受表演和剪辑影响。

### 5.3 建议质量门槛

- 事实性硬错误为 0：不能捏造关键价格、规格、资质、销量、用户证言或明确效果承诺；出现 1 项则该轮评测不通过，修复后复测相关集合。
- 不存在来源 ID 越界、跨品牌引用、未知引用被当作有效依据或未审核内容冒充已审核内容。
- 常规样例五维总体平均分建议不低于 4.0／5，任何单一维度平均分不低于 3.5／5；同时报告逐例分布和低分项，不能用高平均分掩盖硬事实错误。
- 10 个异常场景均按预期拒绝、提示、降级或标明不确定性，不产生越权行为。
- 指标计算和复盘引用的关键数值与确定性结果一致，不让模型重新自由计算正式指标。

这些是**待验证的目标**。如果实际达不到，应缩小适用范围、改进流程或明确限制，不改写报告制造通过。

### 5.4 谁来评、怎样报告

开发者先按统一 rubric 自检，并尽量请一名没有参与 prompt 编写的人复核至少 10 份输出，优先覆盖低分、异常、事实密集和随机选取的样本。先独立评分，再讨论差异，保留分歧。

若没有独立评审者，报告必须写明「开发者人工自检，尚未独立复核」。模型自评可以作为找问题的辅助，不能冒充人工验收或准确率。

可报告「本轮抽查的 N 条事实性陈述中，有 M 条被所提供的来源支持」，并说明样本、评审者和判断规则；不可据此宣称「事实准确率 100%」或保证现实世界真实性。不得把演示数据上的 ROAS 说成实际商业提升。

## 6. 15 个核心端到端验收用例

以下用例全部待执行。自动化应优先覆盖权限、事务、状态和确定性计算；AI 文字质量用上述人工评测补足。无需为每个静态标题或 CSS 类名写测试。

### E01｜访客无密钥完成演示并重置

- **目标**：公开链接能独立展示项目价值。
- **步骤**：无痕窗口打开 demo；依次查看品牌资料、brief、方案、双渠道内容、审核、CSV 和复盘；修改关键品牌事实、brief 或指标；查看旧结果提示；刷新；点击重置。
- **预期**：全程明确标注预生成样例；不要求登录或密钥；不调用付费 AI；关键输入改变后不能冒充产生了新 AI 结果，旧结果明确过期且不能直接正式导出；本地变动按说明保留；重置后恢复种子数据。
- **证据**：完整录像、网络 HAR、重置前后截图。
- **状态**：待验证。

### E02｜真实模式完整业务链

- **目标**：验证真实 AI 路径实际存在，且结果能持久化。
- **步骤**：受保护账号登录；建立品牌事实和活动；填写 brief；生成方案及两个渠道内容；审核一个版本；正式导出；使用导出清单的 variant ID 导入成熟的有效指标；生成复盘；刷新重新打开。
- **预期**：各步骤有可追溯结果；数据刷新后仍存在；导出使用基于当前依据的已批准版本，并原子锁定已交付版本；无需另做登记投放；复盘引用所选指标快照及对应已交付内容，导出状态不冒充发布状态。
- **证据**：录像、执行记录 ID、脱敏数据库记录、导出样本、复盘版本。
- **状态**：待验证。

### E03｜未登录与跨账号访问隔离

- **目标**：证明服务端鉴权和 RLS 均生效。
- **步骤**：用账号 A 建立数据；账号 B 及匿名会话分别尝试通过页面、API、已知记录 ID、导出地址、执行状态查询访问或修改 A 的记录；另测直接数据库客户端路径。
- **预期**：所有越权读取、写入、导出与生成都被拒绝；错误信息不泄露 A 的材料；B 正常访问自己的数据。
- **证据**：接口状态及响应、RLS 集成测试结果、数据库前后快照。
- **状态**：待验证。

### E04｜事实不足、冲突与提示注入

- **目标**：不把输入里的指令或缺失信息变成营销事实。
- **步骤**：分别输入缺价格、冲突价格、虚构认证请求和注入文本；生成内容。
- **预期**：缺失或冲突事实被标为待确认；无捏造认证；注入内容不改变权限、不泄露配置；人能看懂为何需要补资料。
- **证据**：输入快照、原始输出、人工事实核对表。
- **状态**：待验证。

### E05｜结构与引用校验

- **目标**：非法模型响应不能成为可审核的正常结果。
- **步骤**：mock 非法 JSON、必需字段缺失、未知引用、跨品牌引用及越界枚举；再用合法响应验证恢复。
- **预期**：非法结果被明确拒绝，执行不会显示成功；合法结果可保存；页面不会因异常结构崩溃。
- **证据**：结构校验报告、错误页面、数据库执行状态。
- **状态**：待验证。

### E06｜双击与并发重发的幂等性

- **目标**：一项用户意图不重复生成业务结果。
- **步骤**：对同一键并发提交两个相同请求；重发同一请求；再用同一键提交不同输入；最后显式重新生成。
- **预期**：前两类只对应一个执行及业务版本；同键异参被拒绝；显式重新生成产生独立执行和新版本。
- **证据**：并发请求日志、唯一约束测试、执行与内容版本计数。
- **状态**：待验证。

### E07｜重试、超时与结果不明

- **目标**：失败可理解，成本和状态不失控。
- **步骤**：mock 可重试错误后成功、连续可重试错误、20 秒超时、接近 45 秒 deadline、响应后数据库失败及执行进程中断；测试显式重试。
- **预期**：确定可重试错误最多再试 1 次；无隐藏额外 SDK 重试；超时进入 `unknown` 且不盲重调；用户重试前可见再次计费说明；残留运行记录不会永久显示正常处理中。
- **证据**：可控时钟测试、调用次数、时间线、状态截图、日志中的错误分类。
- **状态**：待验证。

### E08｜审核、编辑与历史版本

- **目标**：审核结论绑定到精确内容。
- **步骤**：批准版本 V1，首次正式导出；并发重试导出并检查锁定结果；实质修改文本生成新 variant 的 V2；尝试正式导出 V2；拒绝 V2；重新生成 V3；尝试绕过规则将新素材绑定原 variant；修改品牌事实或 brief；查看 V1 的来源并尝试再次正式导出。
- **预期**：首次正式导出与已交付版本锁定具有事务一致性，重复请求不会改写锁定；实质改稿使用新 variant，V2／V3 不继承批准；未批准版本不能正式导出；原 variant 的已交付版本始终为 V1；V1 及其历史来源仍可追溯；当前依据过期时即使 V1 曾获批准也不能正式导出。
- **证据**：版本时间线、审批记录、导出检查、来源快照截图。
- **状态**：待验证。

### E09｜黄金 CSV 导入与聚合

- **目标**：指标与数学定义完全一致。
- **步骤**：将两个已审核变体 A、B 正式导出并锁定各自交付版本；使用导出清单中的 ID 导入本文黄金样例；分别查看 A、B、合计；切换活动、日期、渠道和 variant 筛选。
- **预期**：原始合计为 30,000／700／20／1,400／5,380；总 CTR 2.333333…%、CVR 2.857142…%、CPC 2、CPA 70、ROAS 3.842857…；筛选后重新由分子分母计算。
- **证据**：CSV 原文件、纯函数测试报告、界面截图、导出指标。
- **状态**：待验证。

### E10｜CSV 错误与原子性

- **目标**：错误文件不污染正式数据。
- **步骤**：构造混合币种、口径不一致、非法日期、空数值、负数、非法渠道、跨账号活动、未正式导出的 variant、缺列、重复列与最后一行错误的文件；逐一预览并尝试导入。
- **预期**：定位到行与列；整个批次拒绝；没有前几行部分落库；原有指标保持不变。
- **证据**：错误文件、错误预览截图、数据库前后行数与金额校验。
- **状态**：待验证。

### E11｜重复文件与自然键冲突

- **目标**：换名字、换顺序也不能默默累加数据。
- **步骤**：同文件导入两次；改文件名后再导入；重新排序后导入；另导入一个仅包含一行自然键冲突的批次。
- **预期**：同 hash 返回已有结果或明确已导入；其他重复由自然键识别；冲突批次整体拒绝；总金额和订单数不增长。
- **证据**：文件 hash、批次记录、冲突明细、数据库唯一约束测试。
- **状态**：待验证。

### E12｜0 分母、缺失值与成熟窗口

- **目标**：稀疏数据不会生成无意义指标或结论。
- **步骤**：导入全零、只有曝光、0 花费有收入、0 订单有点击的数据；预览最近 7 天数据并分别取消、确认警告；查看图表、导出及复盘；尝试用后续回填值重传相同自然键。
- **预期**：0 分母均为 `N/A`；0 分子且有效分母显示 0；无 `Infinity`／`NaN`；未成熟数据须确认警告才能导入，取消不入库；警告说明当前不支持增量修正；同键回填被整批拒绝；AI 不以空数据做绝对优劣结论。
- **证据**：边界数据、指标断言、界面与复盘截图。
- **状态**：待验证。

### E13｜复盘依据与数据更新

- **目标**：AI 解释可核对、可追溯。
- **步骤**：用黄金样例生成复盘；核对所有数字；添加新日期的数据；重新打开旧复盘；生成新复盘；另将业务需求写为首购目标但只提供普通归因订单。
- **预期**：数字与代码计算一致，指标对应锁定的已交付版本；观察、假设、建议分开；不声称真实因果或净利润；旧复盘显示旧快照，新复盘绑定新快照；普通归因订单不能被称为首购订单，额外首购目标显示当前数据不足以验证。
- **证据**：指标快照、人工数字核对表、两次复盘版本。
- **状态**：待验证。

### E14｜导出内容与注入防护

- **目标**：导出可信、可读且不会执行用户输入。
- **步骤**：在允许的文本字段放入 HTML 标签与公式起始字符；生成、预览和导出；检查文件版本、中文编码、引用说明和未审核标识。
- **预期**：页面按文本展示；CSV 文本单元格不会被电子表格当作公式执行；正式内容包仅包含基于当前依据的批准版本，标识能关联到精确内容；文件能正常打开且中文不乱码。
- **证据**：输入样本、导出文件、浏览器截图、电子表格打开检查记录。
- **状态**：待验证。

### E15｜部署、配置缺失与回滚演练

- **目标**：发布后遇到配置或版本问题能够恢复。
- **步骤**：在预览环境执行生产构建；模拟缺少模型密钥；验证公开 demo；部署已知良好版本；发布一个可控故障版本后回滚；验证迁移兼容性和数据恢复方案。
- **预期**：缺密钥时真实模式明确不可用，公开 demo 仍可演示；错误响应不泄露配置；回滚后核心流程恢复；数据未被静默丢弃。
- **证据**：构建日志、部署 ID、回滚前后冒烟结果、恢复步骤实录。
- **状态**：待验证。

## 8. 回滚与恢复方案

MVP 使用简单、可演练的恢复方案即可，不要求引入企业级发布平台。

1. **保留可用版本**：每次发布记录 Git commit、部署 ID、迁移版本及 smoke 结果，保留上一版可访问的 demo。
2. **优先停止扩大问题**：提供服务端开关停用真实生成或指标导入。公开 fixture demo 保持可用，并清楚显示真实功能当前不可用。
3. **回滚应用**：恢复上一已验证部署，再执行登录、读取已有内容、fixture 演示和黄金指标冒烟。
4. **单独处理数据库**：应用回滚不会自动回滚数据库。MVP 迁移优先增加字段或表，避免同次发布直接删除旧字段；对破坏性迁移先做备份并验证恢复。无法兼容时，按预先记录的修复方案操作，不能简单宣称「一键回滚所有数据」。
5. **修复执行状态**：检查遗留的 `running`／`unknown` 记录；在无法确认提供商结果时不批量自动重跑。修复不能再次生成重复结果或重复导入指标。
6. **复盘并复测**：保留问题触发条件、影响范围、恢复步骤和复测证据，修复对应回归测试后重新发布。

建议在预览环境演练一次「模型不可用」、一次「CSV 冲突拒绝」和一次「部署回滚」。演练成功后填写实际恢复耗时；不要预先写不存在的恢复时间承诺。
